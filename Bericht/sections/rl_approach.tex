To use reinforcement learning techniques for modeling the \ac{drausp}, first of all we need to define
a \ac{mdp} that represents the problem. We define a state space,an action space and a transition function: 

\textbf{State space.} A state
\[
  s = (t, \hat C_1, \dots, \hat C_K, r, q_1, \dots, q_K) \in \mathcal{S} \subseteq \mathbb{R}^{2K+2}
\]
consists of the current decision epoch $t \in \{1,\dots,T_d\}$, the remaining capacities
$\hat C_k \in \{0,\dots,C_k^{(0)}\}$ of each resource $k=1,\dots,K$, and the request $[r,q]$
currently up for decision, with reward $r \in \mathbb{R}_{\ge 0}$ and (zero-padded) demand vector
$q \in \mathbb{N}_0^K$. The initial state is $s_1 = (1, C_1^{(0)}, \dots, C_K^{(0)}, r_1, q_1)$.

\textbf{Action space.} $\mathcal{A} = \{0,1,\dots,K\}$: action $a=0$ rejects the current request; action $a \in \{1,\dots,K\}$ accepts it and schedules it starting at slot $a$.
Assume that the current request has length $\ell \in \{1,\dots,K\}$ and demand vector $q = (q_1,\dots,q_\ell,0,\dots,0)$ (zero-padded to length $K$). Then the action $a$ is feasible if and only if 
\begin{itemize}
 \item $a+\ell-1 \le K$, we do not exceed the maximum length of resources
 \item $\hat C_{a+i-1} \ge q_i$ for all $i=1,\dots,\ell$, the capacity of all affected slots is sufficient to accept the request
\end{itemize} 
Note that for a given state not all actions are feasible: We define the feasible action set $\mathcal{A}_s^{\text{valid}} \subseteq \mathcal{A}$ as the set of actions that do not exceed the remaining capacity of any affected slot and do not exceed the horizon $K$.
Nevertheless the set of valid actions $\mathcal{A}_s^{\text{valid}}$ is never empty, since $0 \in \mathcal{A}_s^{\text{valid}}$ for all states $s$.
We will use the set of valid actions later on.

\textbf{Transition function.} $\mathcal{T}: \mathcal{S} \times \mathcal{A} \to \mathcal{S}$
deterministically updates the remaining capacities according to the chosen action, appends the next request
$[r_{t+1}, q_{t+1}]$ drawn from the instance's request sequence, and advances time, $t \mapsto t+1$. 
The new capacities are given by the following equation:
\[
  \hat C_{a+i-1} \;\leftarrow\; \hat C_{a+i-1} - q_i, \qquad i = 1,\dots,\ell.
\]
Note that $\hat{C_k} \geq 0$ for all valid actions $a \in \mathcal{A}_x^{\text{valid}}$ and all $k=1,\dots,K$.

\textbf{Reward.} The reward function $\mathcal{R}: \mathcal{S} \times \mathcal{A} \to \mathbb{R}$ is defined as follows:
\[
  \mathcal{R}(s,a) =
  \begin{cases}
    r, & \text{if } a \in \mathcal{A}_s^{\text{valid}} \setminus \{0\} \\
    0, & \text{if } a = 0 \\
    -100, & \text{if } a \notin \mathcal{A}_s^{\text{valid}}
  \end{cases}
\]
Selecting an infeasible action, terminates the episode and yields a large negative reward of $-100$ to discourage the agent from taking invalid actions.

\textbf{Objective.} What we actually want to learn is the optimal action-value function
$Q^*(s,a)$: given a state $s$ and an action $a$, it returns the maximum expected cumulative
reward obtainable from now, time step $t$, until the end of the horizon $T_d$, if $a$ is taken in $s$ and the
optimal policy is followed afterwards,
\[
  Q^*(s,a) = \max_\pi \; \mathbb{E}\Big[\, \sum_{t'=t}^{T_d} \gamma^{t'-t} \cdot \mathcal{R}(s_{t'}, a_{t'}) \;\Big|\; s_t = s,\, a_t = a \,\Big].
\]
Note that this is not a greedy problem: accepting a request now reduces the remaining capacities $\hat C$
and can make more valuable future requests infeasible, so $Q^*$ has to trade off the immediate
reward $r$ against the option value of keeping capacity free. Once $Q^*$ is known (or
approximated by a trained network), the optimal policy follows directly by acting greedily with
respect to it:
\[
  \pi^*(s) = \arg\max_{a \in \mathcal{A}_s} Q^*(s,a).
\]

\subsection{Zustands- und Aktionsraum}
\label{subsec:state-action}

Das DRAUSP verwaltet $K$ fest angeordnete Kapazitätsslots (Ressourcen) $k=1,\dots,K$ mit
Anfangskapazitäten $C_k^{(0)}$ (z.\,B.\ $C_k^{(0)}=20$ für alle $k$), die über einen
Planungshorizont von $T_d$ Entscheidungsepochen \emph{nie} wieder aufgefüllt werden. Der Zustand
zu Beginn von Epoche $t$ lässt sich als
\begin{equation}
  \label{eq:state}
  s = \big[\, t,\; \hat C_1, \dots, \hat C_K,\; r,\; q_1, \dots, q_K \,\big] \in \mathbb{R}^{2K+2}
\end{equation}
darstellen, wobei $t$ die verstrichene Zeit, $\hat C_k$ die verbleibende Restkapazität von Slot
$k$, $r$ die Belohnung der in Epoche $t$ eintreffenden Anfrage und $q_k$ deren Bedarfsvektor
bezeichnet (\texttt{gymnasium\_env.py}, Klasse \texttt{DrauspEnv}).

\textbf{Anfragen haben variable Länge, der Zustand nicht.} Eine Anfrage belegt bei Annahme keinen
einzelnen Slot, sondern einen \emph{zusammenhängenden Block} von $\ell \in \{1,\dots,K\}$ Slots,
und benötigt dabei für den $i$-ten Slot dieses Blocks $q_i$ Kapazitätseinheiten,
$i = 1,\dots,\ell$. Die Blocklänge $\ell$ variiert von Anfrage zu Anfrage -- im
Instanzgenerator (\texttt{instance\_generator.py}) wird sie gleichverteilt aus
$\{1,\dots,K\}$ gezogen; in Benchmark-Instanzen kann sie auch fix vorgegeben sein
(\texttt{fixed\_request\_length}). Da aber \emph{ein und dasselbe} Netzwerk Zustände zu jeder
Anfrage verarbeiten muss, wird der Bedarfsvektor unabhängig von $\ell$ stets auf die feste Länge
$K$ gebracht, indem er mit Nullen aufgefüllt wird:
\begin{equation}
  \label{eq:padding}
  q = (\underbrace{q_1, \dots, q_\ell}_{\text{tatsächlicher Bedarf}},\; \underbrace{0, \dots, 0}_{K-\ell \text{ Nullen}}\,).
\end{equation}
Entscheidend dabei: Der Index $k$ in $q_k$ bezeichnet \emph{keine} absolute Slotposition im
Zeitplan, sondern die Position \emph{relativ zum (noch nicht feststehenden) Startslot} der
Anfrage. Wo genau dieser Block im Zeitplan liegt, legt erst die Aktion fest.

\textbf{Aktion.} Die Aktion $a \in \{0,1,\dots,K\}$ wählt entweder Ablehnung ($a=0$, Reward $0$)
oder den Startslot $a$, ab dem die Anfrage eingeplant wird. Bei Annahme belegt sie die Slots
$a, a+1, \dots, a+\ell-1$ und reduziert deren Restkapazität um $q_1,\dots,q_\ell$:
\[
  \hat C_{a+i-1} \;\leftarrow\; \hat C_{a+i-1} - q_i, \qquad i = 1,\dots,\ell.
\]
Eine Aktion ist nur gültig, wenn der Block innerhalb des Horizonts liegt ($a+\ell-1 \le K$) und an
jeder betroffenen Slotposition ausreichend Restkapazität vorhanden ist ($\hat C_{a+i-1} \ge q_i$
für alle $i$); ungültige Aktionen werden mit Reward $-20$ bestraft und beenden die Episode.

$\ell=3$ und Startslot $a=2$.

\textbf{Konsequenz für die Monotonie.} Die hinteren $K-\ell$ Einträge von $q$ sind stets $0$ --
der kleinste Wert im kalibrierten Wertebereich von $q_k$. Das ist inhaltlich konsistent mit der
in Abschnitt~\ref{subsec:monotonicity} postulierten DECREASING-Monotonie: Ein Padding-Eintrag
bedeutet "kein Bedarf an dieser relativen Position" und wirkt im kalibrierten Modell wie eine
Anfrage ohne jede Einschränkung an diesem Slot -- was korrekt ist, da dieser Slot vom Block der
aktuellen Anfrage gar nicht betroffen ist.

\textbf{Vergleich mit der Zustands-/Aktionsraum-Formulierung im DRAUSP-Paper.}
\textcite{drausp_lion18} formulieren das DRAUSP ebenfalls als MDP, jedoch mit einem deutlich
schlankeren Zustandsraum. Ihr Zustand ist rein der Kapazitätsvektor
$s_t = cap = (\hat C_1,\dots,\hat C_K) \in S = \{0,\dots,C_1\}\times\dots\times\{0,\dots,C_K\}$;
der Zeitindex $t$ ist dort kein Bestandteil des Zustandsvektors, sondern nur ein separater,
rückwärtslaufender Stufenindex ihrer Rekursion. Insbesondere ist die aktuelle Anfrage $[r,q]$
\emph{nicht} im Zustand enthalten -- sie bestimmt stattdessen direkt die Aktionsmenge $A_s$: Eine
Aktion $a=[a_r,a_q]$ enthält bereits den auf eine konkrete Startposition verschobenen, gepaddeten
Bedarfsvektor als vollen $K$-dimensionalen Vektor, und der Übergang $s_{t-1} = cap - a_q$ ist
deterministisch. Unser Zustand $s$ (Gleichung~\eqref{eq:state}) enthält $r$ und $q$ dagegen
explizit, während unsere Aktion auf den schlanken Startslot $a \in \{0,\dots,K\}$ reduziert ist.
Tabelle~\ref{tab:mdp-comparison} fasst diese strukturelle Gegenüberstellung zusammen; \emph{wie}
die beiden Formulierungen anschließend gelöst werden (exakte dynamische Programmierung vs.\
Funktionsapproximation per DQN), wird gesondert im Abschnitt zum DQN-Agenten behandelt.

Der Zustandsraum aus dem Paper funktioniert für einen RL-Ansatz mit Q-Funktion nicht, 
weil eine Q-Funktion $Q(s,a)$ pro Zustand $s$ einen festen Wert für jede Aktion $a$ liefern soll 
— aber der Wert einer Aktion hängt hier entscheidend davon ab, welche Anfrage gerade vorliegt.
Mit dem zustandsraum, der nur die aktuellen Restkapazitäten berücksichtigt, weiß der Agwnt nicht, 
welche Anfrage er gerade bewertet.

Ein Q-Learning-Agent sollte bei jeder Entscheidung direkt aus dem Zustand ableiten können, wie gut jede Aktion ist.
Dafür muss der Zustand die Anfrage enthalten, damit der Agent die Belohnung und den Ressourcenbedarf kennt.

\subsection{Monotonicity in the Q-Function}
\label{subsec:monotonicity}

Für den in Gleichung~\eqref{eq:state} eingeführten Zustand $s$ lassen sich plausible
monotone Beziehungen zwischen einzelnen Zustandsgrößen und dem optimalen $Q$-Wert postulieren:

\begin{itemize}
  \item $t$ \textbf{(DECREASING)}: Je mehr Zeit bereits verstrichen ist, desto weniger
        zukünftige Anfragen können noch angenommen werden -- der erwartete Restwert sinkt.
  \item $C_k$ \textbf{(INCREASING)}: Mehr Restkapazität einer Ressource kann den zukünftigen
        Handlungsspielraum nur vergrößern, nie verkleinern.
  \item $r$ \textbf{(INCREASING)}: Eine Anfrage mit höherer Belohnung ist bei sonst gleichen
        Bedingungen nie schlechter zu bewerten als eine mit niedrigerer Belohnung.
  \item $q_k$ \textbf{(DECREASING)}: Ein höherer Ressourcenbedarf der aktuellen Anfrage schränkt
        die verbleibende Kapazität stärker ein und kann den Wert der Annahme nur verringern.
  \end{itemize}

Ein Standard-DQN (vgl.\ \texttt{standard\_dqn.py}) approximiert $Q(s,a)$ mit einem generischen
Feedforward-Netz und hat keine Garantie, diese Beziehungen einzuhalten. Statt Monotonie nur als
weichen Strafterm in der Verlustfunktion zu fordern, bauen wir sie \emph{strukturell} in die
Netzwerkarchitektur ein: Ein \emph{Lattice-Netzwerk} approximiert eine mehrdimensionale Funktion
durch (multi-)lineare Interpolation auf einem regelmäßigen Gitter aus lernbaren Stützwerten.
Ist jeder Stützwert entlang einer Gitterachse monoton angeordnet, ist die gesamte interpolierte
Funktion entlang dieser Achse garantiert monoton -- unabhängig vom Training. Dieses Prinzip wird
in den Modellen \texttt{full\_lattice.py} und \texttt{deep\_lattice.py} umgesetzt und im Folgenden
für das zweistufige \emph{Deep-Lattice}-Netzwerk beschrieben.

\subsection{Deep Lattice Network Architektur}
\label{subsec:deep-lattice}

Ein einzelnes Lattice mit $d$ Eingängen besitzt $2^d$ lernbare Eckgewichte (bei Gittergröße~2 je
Achse) und wird durch $d$-lineare Interpolation ausgewertet -- Abbildung~\ref{fig:lattice-cube}
zeigt dies exemplarisch für $d=3$. Mit wachsendem $d$ wächst die Anzahl der Eckgewichte jedoch
exponentiell ($2^d$), weshalb ein einzelnes Lattice über alle $2+2K$ Zustandsgrößen für DRAUSP-
Instanzen mit mehreren Ressourcen $K$ schnell unpraktikabel wird (vgl.\ \texttt{full\_lattice.py}).
Das \emph{Deep-Lattice}-Netzwerk (\texttt{deep\_lattice.py}) löst dies, indem es viele kleine
3-Input-Lattices in zwei hintereinandergeschalteten Schichten kombiniert -- ähnlich einem tiefen
neuronalen Netz, jedoch mit an jeder Schicht erhaltener End-to-End-Monotonie. Abbildung~\ref{fig:deep-lattice-architecture}
skizziert die Architektur für $K=2$ Ressourcen.

\textbf{Schicht 0 -- Kalibratoren.} Jedes Rohfeature ($t$, $C_k$, $r$, $q_k$) durchläuft einen
eigenen \texttt{NumericalCalibrator}: eine stückweise lineare, monotone Funktion, die den Wert auf
$[0,1]$ abbildet und dabei die in Abschnitt~\ref{subsec:monotonicity} festgelegte
Monotonierichtung (INCREASING/DECREASING) ein für alle Mal kodiert. Alle nachfolgenden Schichten
müssen dadurch nur noch \emph{increasing} sein.

\textbf{Schicht 1 -- Intra-Resource-Lattice-Ensemble.} Für jede Ressource $k$ werden die
kalibrierten Features zu drei fachlich motivierten 3er-Gruppen kombiniert:
$A_k = [t, r, C_k]$ (Zeitdruck/Belohnung/Kapazität),
$B_k = [C_k, q_k, r]$ (Kapazität/Bedarf/Belohnung) und
$C_k = [t, C_k, q_k]$ (Zeitdruck/Kapazität/Bedarf).
Jede Gruppe wird von \texttt{lattice\_units} vielen unabhängigen $2\times2\times2$-Lattices
(Ensemble) verarbeitet, sodass Schicht~1 mehrere alternative nichtlineare, aber garantiert
monotone Kombinationen dieser Größen lernen kann.

\textbf{Zwischenkalibratoren.} Jeder einzelne Lattice-Output aus Schicht~1 erhält einen eigenen
\texttt{NumericalCalibrator} (monoton \emph{increasing}), der ihn zurück auf $[0,1]$ normalisiert
-- notwendig, damit er in Schicht~2 wieder als gültige Gitterkoordinate verwendet werden kann.

\textbf{Schicht 2 -- Cross-Resource-Lattices.} Während Schicht~1 nur Interaktionen
\emph{innerhalb} einer Ressource $k$ modellieren kann, kombiniert Schicht~2 gezielt je einen
kalibrierten Output aus Gruppe $A$, $B$ und $C$ unterschiedlicher Ressourcen $k$ zu neuen
3-Input-Lattices. So kann das Netz z.\,B.\ lernen, wie die Kapazitätssituation von Ressource~1 mit
dem Zeitdruck-Belohnungs-Profil von Ressource~2 zusammenwirkt -- eine Interaktion, die Schicht~1
strukturell nicht abbilden kann. Ein rotierender Ressourcen-Offset erzeugt dabei genau $K$ solcher
Tripel (statt aller $K^3$ möglichen Kombinationen), sodass Schicht~2 linear und nicht kubisch mit
der Ressourcenzahl $K$ wächst.

\textbf{Output-Layer.} Ein \texttt{Linear}-Layer aggregiert alle Schicht-2-Outputs zu einem
$Q$-Wert pro Aktion. Seine Gewichte werden nach jedem Optimierungsschritt auf $\geq 0$ geklemmt
(\texttt{apply\_constraints()}), sodass eine positive (monotone) Wirkung aus den vorangehenden
Schichten nicht durch negative Gewichte im letzten Schritt umgekehrt werden kann. Damit ist
$Q(s,a)$ end-to-end monoton in $t$, $C_k$, $r$ und $q_k$ -- durch die Architektur erzwungen, nicht
nur durch das Training angestrebt.

\textbf{Berechnung des Funktionswerts.} Der Wert $\hat Q$ an einem beliebigen Punkt
$(x_1,x_2,x_3) \in [0,1]^3$ im Würfel ist \emph{keine} achsenweise Multiplikation eines
einzelnen kalibrierten Werts mit einem einzelnen Eckgewicht, sondern eine gewichtete Summe über
\emph{alle} $2^3=8$ Ecken. Das Gewicht jeder Ecke ist dabei das Produkt der drei
Achsen-Interpolationsfaktoren, je nachdem auf welcher Seite jeder Achse die Ecke liegt (Faktor
$x_a$ auf der $1$-Seite, Faktor $1-x_a$ auf der $0$-Seite):
\begin{equation}
  \label{eq:trilinear}
  \hat Q(x_1,x_2,x_3) = \sum_{i,j,k \in \{0,1\}}
    \big[i\,x_1 + (1-i)(1-x_1)\big]\,
    \big[j\,x_2 + (1-j)(1-x_2)\big]\,
    \big[k\,x_3 + (1-k)(1-x_3)\big]\;
    \theta_{ijk}.
\end{equation}
Diese acht Koeffizienten summieren sich stets zu $1$, sodass $\hat Q$ immer eine Konvexkombination
der acht Eckgewichte ist (\emph{trilineare Interpolation}). Zur Veranschaulichung das
zweidimensionale Analogon mit nur vier Ecken $\theta_{00}, \theta_{10}, \theta_{01}, \theta_{11}$:
\[
  \hat Q(x_1,x_2) = (1-x_1)(1-x_2)\,\theta_{00} + x_1(1-x_2)\,\theta_{10}
                   + (1-x_1)x_2\,\theta_{01} + x_1 x_2\,\theta_{11}.
\]
Für $x_1=x_2=0$ liefert dies exakt $\theta_{00}$, für $x_1=x_2=1$ exakt $\theta_{11}$; dazwischen
wird bilinear (bzw.\ im 3-Input-Fall trilinear) interpoliert. Implementiert ist dies als
äußeres Produkt der achsenweisen Gewichte $(1-x_a, x_a)$ gefolgt von einem Skalarprodukt mit dem
Eckgewichts-Vektor (\texttt{pytorch\_lattice/layers/lattice.py},
\texttt{\_compute\_hypercube\_interpolation}).
